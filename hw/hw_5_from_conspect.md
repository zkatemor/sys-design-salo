# Практическое задание 1.16: выбор rate limiting

# Артефакт 1. Матрица решений для rate limiting

## Контекст

Есть сервис поиска авиабилетов.

Сервис работает в нескольких репликах, поэтому запросы пользователей могут попадать на разные инстансы.

Нужно добавить rate limiting, чтобы защитить сервис от слишком большого количества запросов.

Требования:

- не больше `100 запросов в минуту` с одного IP;
- не больше `1000 запросов в минуту` с одного API-key;
- сервис должен оставаться быстрым;
- решение должно работать при нескольких репликах сервиса.

---

## Варианты

### Вариант 1. Локальный rate limiter внутри сервиса

Каждый инстанс сервиса сам считает запросы.

```text
client -> search-service instance -> local counter
```

Плюсы:

- просто реализовать;
- очень быстро;
- не нужна внешняя инфраструктура.

Минусы:

- плохо работает, если сервис запущен в нескольких репликах;
- каждый инстанс считает лимит отдельно;
- общий лимит может быть превышен;
- после рестарта инстанса счётчики потеряются.

---

### Вариант 2. Rate limiting через API Gateway

Ограничение запросов делает API Gateway перед сервисом.

```text
client -> API Gateway -> search-service
```

Плюсы:

- быстро внедрить;
- не нужно писать много своего кода;
- удобно для стандартных правил.

Минусы:

- зависимость от API Gateway;
- может быть сложнее настроить нестандартные правила;
- может появиться дополнительная стоимость;
- меньше контроля над логикой.

---

### Вариант 3. Rate limiting через Redis

Сервис проверяет лимиты через Redis. Redis хранит общие счётчики для всех реплик.

```text
client -> search-service -> Redis
```

Плюсы:

- работает корректно при нескольких репликах;
- можно гибко настраивать правила;
- Redis быстрый;
- команда может контролировать логику.

Минусы:

- появляется внешняя зависимость;
- если Redis недоступен, нужно решить, что делать;
- Redis нужно мониторить.

---

## Матрица решений

Оценка:  
`1` – плохо, `5` – хорошо.

| Критерий | Вес | Локально в сервисе | API Gateway | Redis |
|---|---:|---:|---:|---:|
| Простота реализации | 3 | 5 | 4 | 3 |
| Корректность при нескольких репликах | 3 | 1 | 5 | 5 |
| Гибкость правил | 2 | 4 | 3 | 5 |
| Скорость работы | 1 | 5 | 4 | 4 |
| Простота поддержки | 1 | 4 | 5 | 3 |
| **Итого** | **10** | **33** | **43** | **43** |

---

## Вывод по матрице

По баллам `API Gateway` и `Redis` получили одинаковый результат.

Но для нашего случая выбираем **Redis**, потому что:

- нам нужны лимиты, которые работают одинаково для всех реплик сервиса;
- Redis даёт больше контроля над логикой;
- в будущем будет проще добавить новые правила, например лимит по пользователю или партнёру;
- Redis достаточно быстрый для такой задачи.

Локальный rate limiter не выбираем, потому что он некорректно работает в системе с несколькими репликами.

# Артефакт 2. ADR

# ADR-0002: Rate limiting через Redis

**Дата:** 2026-05-04  
**Статус:** Accepted

---

## Контекст

Сервис поиска авиабилетов работает в нескольких репликах.

Нужно ограничивать количество запросов:

- `100 запросов в минуту` с одного IP;
- `1000 запросов в минуту` с одного API-key.

Rate limiting нужен, чтобы:

- защитить сервис от перегрузки;
- ограничить злоупотребления;
- не дать одному пользователю или клиенту занять слишком много ресурсов.

Рассмотрели три варианта:

1. Локальный rate limiter внутри сервиса.
2. Rate limiting через API Gateway.
3. Rate limiting через Redis.

---

## Решение

Выбираем **rate limiting через Redis**.

Redis будет хранить счётчики запросов. Все реплики сервиса будут обращаться к одному Redis, поэтому лимиты будут общими для всей системы.

Пример логики:

1. Приходит запрос.
2. Сервис определяет IP и API-key.
3. Сервис проверяет счётчик в Redis.
4. Если лимит не превышен – запрос выполняется.
5. Если лимит превышен – возвращаем ошибку `429 Too Many Requests`.

---

## Последствия

### Плюсы

- Лимиты работают корректно при нескольких репликах сервиса.
- Можно гибко добавлять новые правила.
- Redis быстрый и подходит для счётчиков.
- Бизнес-логика остаётся под контролем команды.

### Минусы

- Redis становится дополнительной зависимостью.
- Нужно мониторить Redis.
- Нужно решить, что делать, если Redis временно недоступен.

---

## Риски

### Риск 1. Redis недоступен

Если Redis недоступен, сервис не сможет проверить лимиты.

Что делаем:

- временно разрешаем запросы, чтобы не ломать поиск для пользователей;
- логируем ошибку;
- добавляем алерт для команды.

Такой подход называется `fail-open`.

---

### Риск 2. Redis работает медленно

Если Redis отвечает медленно, это может замедлить поиск.

Что делаем:

- ставим короткий timeout на запрос к Redis;
- мониторим время ответа Redis;
- добавляем алерт, если Redis начинает отвечать медленно.

---

### Риск 3. Один пользователь обходит лимит

Например, пользователь меняет IP или API-key.

Что делаем:

- сначала ограничиваем по IP и API-key;
- позже можно добавить лимит по user-id;
- для подозрительных клиентов можно сделать отдельные правила.

---

## Итог

Выбран Redis-based rate limiting.

Это решение немного сложнее, чем локальный счётчик, но оно корректно работает в распределённой системе с несколькими репликами.

API Gateway тоже подходит, но Redis даёт больше гибкости и контроля над логикой.
