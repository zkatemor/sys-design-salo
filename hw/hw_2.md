# 1. Расчёт нагрузки (Back-of-the-envelope)

## 1.1 Исходные данные

Бизнес предоставил следующие параметры:

- ожидаемая аудитория: **20 000 пользователей / месяц**
- пользователь выполняет в среднем **≈ 5 поисков**
- соотношение **поиск : бронирование = 100 : 1**
- пиковая активность: **20% суточного трафика за 3 часа**
- B2B API должен отвечать **< 5 секунд**
- сервис работает **только в РФ (ФЗ-152)**

---

# 1.2 Базовая нагрузка

Пользователей в день:

20 000 / 30 ≈ **667 пользователей**

Поисков в день:

667 × 5 = **3 335 поисков**

Базовый RPS:

3 335 / 86 400 ≈ **0.04 RPS**

Пиковый RPS:

3 335 × 0.2 / 10 800 ≈ **0.062 RPS**

### Вывод

Начальная нагрузка очень низкая (<1 RPS).  
Проектировать систему только под текущую нагрузку рискованно, поэтому архитектура должна учитывать **будущий рост аудитории и маркетинговые всплески**.

---

# 1.3 Планирование роста

Допущения:

- рост аудитории **×20 за 12 месяцев**
- маркетинговые акции создают **spike ×5**

Пользователи через год:

20 000 × 20 = **400 000 пользователей / месяц**

Пользователи в день:

400 000 / 30 ≈ **13 333 пользователей**

Поисков в день:

13 333 × 5 = **66 665 поисков**

Пиковый RPS:

66 665 × 0.2 / 10 800 ≈ **1.23 RPS**

С учётом акционного spike:

1.23 × 5 ≈ **6 RPS**

### Проектная нагрузка

Система проектируется на:

**20 RPS**

Это даёт:

- запас ×3 к ожидаемому пику
- возможность масштабирования без изменения архитектуры

---

# 1.4 Нагрузка на бронирование

Соотношение операций:

поиск : бронирование = **100 : 1**

Бронирований в день:

66 665 / 100 ≈ **667 бронирований**

Базовый RPS:

667 / 86 400 ≈ **0.0077 RPS**

Пиковый RPS:

667 × 0.2 / 10 800 ≈ **0.012 RPS**

### Проектная нагрузка

Сервис бронирования проектируется на:

**5–10 TPS**

Это обеспечивает запас для:

- flash-sales
- партнёрских интеграций
- роста продукта

---

# 2. NFR: Производительность (Latency & Throughput)

## 2.1 Сервис поиска

| Метрика | Значение | Обоснование |
|--------|---------|-------------|
| p50 latency | < 500 ms | большинство запросов должны возвращаться быстро |
| p95 latency | < 1500 ms | fan-out к внешним API |
| p99 latency | < 3000 ms | запас для B2B SLA <5 сек |
| throughput | 20 RPS | проектная нагрузка |

### Обоснование

Сервис поиска работает как **метапоисковый агрегатор**.

Один пользовательский запрос может обращаться к нескольким источникам данных:

- API авиакомпаний  
- OTA (online travel agencies)  
- глобальные системы бронирования **GDS (например Amadeus, Sabre)**  

Каждый поставщик имеет собственную latency, поэтому итоговое время ответа включает:

- сетевые задержки
- время ответа внешних API
- агрегацию и нормализацию результатов

Поэтому p95 ≈ 1–1.5 секунды является реалистичной целью для агрегатора авиабилетов.

---

## 2.2 Degraded mode

| Метрика | Значение |
|-------|----------|
| p95 latency | < 200 ms |

### Стратегия деградации

Если внешние API недоступны, система переходит в **degraded mode**:

- результаты возвращаются из кэша
- показываются ранее найденные маршруты
- медленные поставщики отключаются через **circuit breaker**

Это предотвращает **каскадные отказы** и позволяет системе продолжать работу.

---

## 2.3 Кэширование результатов поиска

Результаты поиска кэшируются в Redis.

TTL: **5–15 минут**

Это допустимо, потому что:

- цены могут немного измениться
- финальная проверка выполняется при бронировании

Кэширование позволяет:

- уменьшить latency
- снизить нагрузку на API партнёров
- обеспечить degraded mode

---

## 2.4 Сервис бронирования

| Метрика | Значение | Обоснование |
|--------|---------|-------------|
| p50 latency | < 1000 ms | запись бронирования |
| p95 latency | < 3000 ms | проверка доступности |
| p99 latency | < 8000 ms | внешний платёж до 5 сек |
| throughput | 10 TPS | запас к расчетной нагрузке |

### Обоснование

Бронирование включает:

- проверку наличия мест
- создание записи бронирования
- взаимодействие с платёжным шлюзом

Поскольку платёжные API могут отвечать до нескольких секунд, p99 latency допускается выше, чем для поиска.

Бизнес-приоритет:

> надёжность бронирований важнее скорости поиска

---

# 3. NFR: Надёжность

## 3.1 Availability

| Компонент | Availability | Downtime/год | Обоснование |
|-----------|-------------|--------------|-------------|
| Поиск | 99.9% | ~8.7 часов | допустима деградация |
| Бронирование | 99.95% | ~4.4 часа | финансовые операции |
| Платёжный шлюз | 99.9% | — | внешний SLA |

Каждая дополнительная "девятка" резко увеличивает стоимость инфраструктуры.

Для стартапа выбран компромисс между стоимостью и необходимой надёжностью.

---

## 3.2 Durability

| Тип данных | RPO | RTO | Механизм |
|-----------|----|----|---------|
| Бронирования | 0 | 5 мин | PostgreSQL + синхронная реплика |
| История поисков | 1 час | 4 часа | асинхронная реплика |
| Кэш | N/A | <1 мин | Redis |

Потеря данных бронирования может привести к:

- финансовым потерям
- конфликтам с авиакомпаниями
- репутационному ущербу

Поэтому используется **синхронная репликация**.

---

# 4. NFR: Консистентность

| Операция | Модель | Обоснование |
|----------|--------|-------------|
| Проверка наличия мест | Eventual consistency | данные быстро обновляются |
| Цены в поиске | Eventual consistency | допускается небольшая задержка |
| Создание бронирования | Strong consistency | нельзя продать одно место дважды |
| История бронирований | Read-your-writes | пользователь должен видеть своё бронирование |

Для предотвращения **double booking** используются:

- транзакции базы данных
- уникальные ограничения
- идемпотентные операции

---

# 5. NFR: Масштабируемость

## Масштабирование поиска

- stateless сервис
- горизонтальное масштабирование
- Redis cache
- autoscaling по CPU/RPS

Stateless архитектура позволяет быстро добавлять новые инстансы во время пиковых нагрузок.

---

## Масштабирование бронирования

- stateless API
- PostgreSQL primary + standby
- connection pooling

---

## Предусловия горизонтального масштабирования

- отсутствие состояния в памяти
- идемпотентные операции
- таймауты и retry
- circuit breaker для внешних API

---

# 6. Ограничения и допущения

- персональные данные пользователей должны храниться **в пределах РФ (ФЗ-152)**
- система зависит от внешних поставщиков:
  - API авиакомпаний  
  - GDS  
  - платёжные шлюзы
- эти системы находятся вне нашего контроля, поэтому архитектура должна учитывать:
  - нестабильную latency
  - возможные отказы
- перед production-запуском требуется **нагрузочное тестирование**

| NFR требование | Архитектурное решение | Причина |

## 2. Архитектурные принципы системы

| Принцип | Реализация |
|---|---|
| Stateless сервисы | Поиск и API не хранят состояние между запросами |
| Горизонтальное масштабирование | Добавление инстансов сервиса под нагрузкой |
| Изоляция внешних зависимостей | Таймауты, retry, circuit breaker |
| Graceful degradation | Работа системы при отказе внешних API |
| Разделение сервисов | Поиск и бронирование реализованы как отдельные сервисы |
| Использование кэша | Redis для ускорения поиска |

---

## 3. Основные архитектурные риски

| Риск | Потенциальная проблема | Способ снижения |
|---|---|---|
| Медленные API авиакомпаний | Рост latency поиска | Timeout + partial results |
| Перегрузка внешних API | Ошибки поиска | Rate limiting + cache |
| Конкурентные бронирования | Double booking | Транзакции и блокировки |
| Рост нагрузки | Увеличение latency | Горизонтальное масштабирование |
| Отказ базы данных | Потеря бронирований | Репликация и failover |

---

## 4. Ключевые выводы

1. NFR напрямую определяют архитектуру системы.
2. Сервис поиска должен быть оптимизирован под latency и масштабируемость.
3. Сервис бронирования должен обеспечивать сильную консистентность и сохранность данных.
4. Использование кэширования и degraded mode критично для устойчивости системы.
5. Архитектура должна учитывать внешние зависимости и регуляторные ограничения.
