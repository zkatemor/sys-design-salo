# 📊 TCO сравнение: Redis Cluster vs PostgreSQL (хранение сессий)

## 1. Цель

Рассчитать и сравнить TCO двух вариантов хранения сессий:
- Redis Cluster
- PostgreSQL

Горизонт расчёта: **2 года**  
Рост нагрузки: **×2 в год**

---

## 2. Входные данные

| Параметр | Значение |
|---------|--------|
| MAU | 400 000 |
| Design RPS | 20 |
| TTL сессии | 30 минут |
| Размер сессии | 1 KB |
| Активные сессии (с запасом) | ~100 000 |

📌 Согласно capacity planning:  
Design RPS рассчитывается через цепочку:  
MAU → DAU → requests/day → peak → spike → headroom.

---

## 3. Архитектурные варианты

### Вариант A: Redis Cluster
- 3 ноды (cluster)
- In-memory хранение
- TTL встроен

### Вариант B: PostgreSQL
- 2 ноды (Primary + Standby)
- Хранение на SSD
- Очистка через cron/vacuum

---

## 4. ROM-оценка

| Вариант | Optimistic | Most Likely | Pessimistic | ROM ($/мес) |
|--------|-----------|------------|-------------|-------------|
| Redis | 100 | 300 | 800 | ~350 |
| PostgreSQL | 80 | 200 | 500 | ~230 |

📌 ROM (Rough Order of Magnitude) – грубая оценка с точностью −50% / +100%.

**Вывод:** PostgreSQL выглядит дешевле на уровне ROM.

---

## 5. Детальный TCO

📌 Формула:
TCO = Infrastructure + People + Hidden Costs


(с учётом временного горизонта)

---

### 5.1 Инфраструктура ($/мес)

| Компонент | Redis | PostgreSQL |
|----------|------:|-----------:|
| Compute | 150 | 180 |
| Storage | 20 | 50 |
| Network | 30 | 0 |
| **Итого** | **200** | **230** |

📌 Инфраструктура включает compute, storage и network расходы.

---

### 5.2 Люди ($/мес)

| Компонент | Redis | PostgreSQL |
|----------|------:|-----------:|
| Setup (амортизировано) | 30 | 90 |
| Поддержка | 80 | 350 |
| On-call | 40 | 150 |
| **Итого** | **150** | **590** |

📌 Люди – ключевая статья TCO (обычно 40–60%).  
📌 On-call имеет стоимость даже без инцидентов из-за потери продуктивности.

---

### 5.3 Скрытые расходы ($/мес)

| Компонент | Redis | PostgreSQL |
|----------|------:|-----------:|
| Tech debt | 50 | 150 |
| Риски деградации | 0 | 50 |
| **Итого** | **50** | **200** |

📌 Скрытые расходы включают:
- технический долг  
- миграции  
- стоимость downtime  

---

## 6. Общий TCO (в месяц)

| Вариант | Инфраструктура | Люди | Скрытые | **Итого ($/мес)** |
|--------|--------------:|------:|--------:|-----------------:|
| Redis | 200 | 150 | 50 | **400** |
| PostgreSQL | 230 | 590 | 200 | **1020** |

---

## 7. Учет роста нагрузки

Рост нагрузки:
Load(t) = Load₀ × 2^t


Через 2 года:
Load = ×4


| Вариант | Старт ($/мес) | Через 2 года ($/мес) |
|--------|--------------:|---------------------:|
| Redis | 400 | ~800 |
| PostgreSQL | 1020 | ~2000 |

📌 TCO нельзя считать как monthly × N месяцев – нагрузка растёт.

---

## 8. TCO за 2 года

| Вариант | TCO |
|--------|-----|
| Redis | ~12 000 $ |
| PostgreSQL | ~28 000 $ |

---

## 9. Сравнение trade-offs

| Критерий | Redis | PostgreSQL |
|---------|------|------------|
| Latency | низкий (RAM) | выше (SSD) |
| Масштабирование | горизонтальное | сложнее |
| TTL | встроен | требует логики |
| Нагрузка на основную БД | отсутствует | высокая |
| Операционная сложность | средняя | высокая |

📌 RAM существенно быстрее SSD → in-memory решения дают меньшую задержку.

---

## 10. Вывод

Несмотря на более низкую стоимость инфраструктуры, PostgreSQL имеет значительно более высокий TCO.

Основные причины:
- более дорогая поддержка
- высокая on-call нагрузка
- накопление технического долга
- худшая масштабируемость

📌 Частая ошибка - сравнивать только инфраструктуру, игнорируя стоимость людей.

---

## 11. Итог

👉 **Redis Cluster является более экономически эффективным решением**  
для хранения сессий при росте нагрузки.
