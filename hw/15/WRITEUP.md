# ДЗ-15. Кэширование `GET /search` – стратегия и замеры

**Сервис:** учебный search API (`cmd/api` → upstream 300 ms)  
**Связь с кейсом авиапоиска:** [hw_2.md](../hw_2.md) – TTL кэша результатов **5–15 мин**, финальная проверка при бронировании.

---

## 1. Стратегия кэширования

**Выбрано: cache-aside (lazy loading) через read-through `GetOrLoad`.**

| Критерий | Почему cache-aside |
|----------|-------------------|
| Записи в каталог | Сервис **не пишет** в upstream – только читает |
| Write-through | Нет смысла: нет синхронной записи в кэш при обновлении каталога |
| Write-behind | Не применимо (read-only endpoint) |

При промахе: loader → upstream → `Set` в in-memory кэш. При обновлении каталога (раз в 30 мин) достаточно **TTL** – event-based инвалидация опциональна на следующем этапе (Redis + Kafka).

**Альтернатива (отвергнута):** только CDN – не подходит для персонализированного/динамического поиска с query `q`.

---

## 2. TTL

**Выбрано: `10 minutes`** (`search.DefaultCacheTTL`).

| Фактор | Значение | Влияние на TTL |
|--------|----------|----------------|
| Переиндексация каталога (TASK) | раз в **30 мин** | Верхняя граница TTL ≤ 30 мин |
| Обновление цен (конспект / hw_2) | **3–5 мин** / 5–15 мин кэш | Нижняя граница свежести |
| SLA P99 без кэша | ~300 ms | Кэш даёт P99 **< 50 ms** на hit |
| Допустимая stale (конспект) | до **5 мин** | 10 мин – компромисс hit-rate vs свежесть |

**Почему не 30 мин:** дольше окно устаревших цен/наличия для «длинного хвоста» запросов (Zipf: топ-100 = 80% трафика – они всё равно часто обновятся по TTL при пиках).

**Почему не 1 мин:** hit-rate падает, upstream нагрузка растёт; при 200 RPS на один `q` выгода кэша снижается.

**Jitter (рекомендация для prod):** `TTL = 10m + random(0..60s)` – размазывает одновременное истечение ключей (thundering herd на границе TTL).

---

## 3. Thundering herd

**Механизм: `golang.org/x/sync/singleflight` в `cache.GetOrLoad`.**

- Параллельные промахи по одному ключу **схлопываются** в один вызов `loader`.
- Тест `TestGetOrLoadSingleflight`: **50** горутин → **1** вызов loader.
- Double-checked locking: быстрый `Get` до и после `singleflight.Do`.

**Без singleflight:** при cold miss 200 запросов → 200× upstream (300 ms каждый) – см. baseline ниже.

---

## 4. Ключ и сериализация

- **Ключ:** строка запроса `q` (нормализация: trim/lowercase – опционально в prod).
- **Значение:** JSON-массив `[]Result` (`internal/search/client.go`).
- **Уровень:** in-process L1 (достаточно для учебного стенда; в prod – L2 Redis по [hw_2](../hw_2.md)).

## 5. Замеры (`scripts/bench.sh`, N=200, `q=golang`)

### До кэша (ожидаемо по TASK)

| Метрика | Значение |
|---------|----------|
| upstream `calls` | **≈ 200** (каждый запрос бьёт в upstream) |
| p99 latency | **≈ 0.30 s** |

### После кэша + singleflight (фактический прогон)

```text
== latency ==
p50: 0.005855 s
p99: 0.311443 s
wall: 4405 ms

== upstream stats ==
calls=1
```

| Метрика | До | После | Улучшение |
|---------|-----|--------|-----------|
| upstream `calls` | ~200 | **1** | **−99.5%** нагрузки на upstream |
| p50 (клиент) | ~300 ms | **~6 ms** | **~50×** на повторных/пакетных запросах |
| p99 | ~300 ms | ~311 ms* | Первая волна ждёт один upstream ~300 ms |

\* p99 отражает первую пачку параллельных запросов, ожидающих единственный `loader`; последующие волны (`xargs -P50`) попадают в кэш с p50 ~6 ms.

**Как воспроизвести:**

```bash
go run ./cmd/upstream &
go run ./cmd/api &
./scripts/bench.sh
curl http://localhost:9090/admin/stats   # calls=1
```

## 6. Метрики (prod)

| Метрика | Цель |
|---------|------|
| `cache_hit_rate` | > 70% (Zipf-трафик) |
| `cache_load_duration_seconds` | p99 < 350 ms (upstream + marshal) |
| `upstream_search_calls_total` | снижение пропорционально hit rate |

---

## 7. Итог

Реализован **in-memory cache-aside** с **TTL 10 min** и **singleflight** для `GET /search`. Bench подтверждает: при 200 параллельных одинаковых запросах upstream вызывается **1 раз**, медианная latency на hit – **порядка единиц ms**.
